## Verified working

- **Authentication.** Bearer tokens are stored as SHA-256 digests, compared in constant time, and
  expire. A missing or invalid token, a `Basic` scheme, or a role header gets 401. Every read and
  write is limited to the manager's assigned employees; unknown and unassigned ids both give 404.
- **SQL.** Every value is parameterized. The f-strings only insert constants and `?` placeholder
  lists. A SQL-injection string in a filter returns 0 rows.
- **The decision workflow.** An eligible proposal is approved, and its correction applied, in one
  transaction. Replaying the same idempotency key returns `replayed: true`. The same key with a
  different body gives 409. A second approval gives 409 (stale). A stale `evidence_version` gives 409
  with the current version. A manager's own unproven edit (late arrival moved to the schedule start)
  gives 422 and is audited as `APPROVAL_BLOCKED`. Unknown fields and a reject without a reason give
  422. Bulk decisions return per-item 404/200.
- **Integrity in PostgreSQL.** UPDATE and DELETE are refused by triggers on `audit_events`,
  `decisions`, `corrections`, `punches`, `proposals` and `llm_traces`. The audit hash chain verifies.
  The `db_maintenance verify` run found 0 problems. Raw model text is purgeable by design (retention).
- **Imports.** A row for another manager's employee is invalid, and a commit containing it is refused
  (422). The limits are 2 MB and 5,000 rows, so a 7.6 MB upload is refused in 0.1 s.
- **AI pipeline.** In live runs every case passed its gates. Proposals for missing punches came out
  eligible with an `evidence_ref`, and unsupported or under-evidenced cases were never eligible.

### A1 (High): a split shift evades the meal-break rule

The meal check runs per work session, and each new session starts a fresh 5-hour count. So a
clock-out at 13:00 and a clock-in at 13:01 satisfy the rule, although no 60-minute rest was taken.
A recorded 1-minute *break* is correctly a violation; a 1-minute *gap between sessions* is not.

| 9 h day, IN-KA (60 min rest after 5 h) | Meal outcome |
| --- | --- |
| No break | violation (correct) |
| Break 13:00-14:00 | pass (correct) |
| Break punch 13:00-13:01 | violation (correct) |
| Clock-out 13:00, clock-in 13:01, no break | **pass (wrong)** |

Fix: treat the gap between consecutive work sessions as a rest only when it lasts at least
`rest_minutes`; otherwise carry the work-time count across the gap. Add the case above as a test.

### A2 (High): one global write lock is held for the whole model call

`ResolutionStore.propose` opens a write transaction (PostgreSQL: `pg_advisory_xact_lock(_WRITE_LOCK)`,
one lock for the whole database; SQLite: `BEGIN IMMEDIATE`). It then runs `generate_proposal` inside
it, including retrieval embeddings and the LLM call (up to 8 s plus a repair retry). Every other
proposal, decision and import from every manager waits for that lock. Measured with Qwen2.5-7B:
three concurrent proposals finished at 8.9 s, 15.8 s and 22.3 s, so they were fully serialized. Ten
managers pressing "propose" at once would make the last wait about 70 s.

Fix: run the pipeline outside the write transaction. Load the case and the totals in a short read
transaction, call `generate_proposal`, then open a short write transaction that re-checks the
correction revision (stale gives 409, or drop the result) and inserts the proposal, trace and audit
event. Approval already re-validates against fresh evidence, so nothing relies on the long lock.

### A3 (Medium): a reused `X-Trace-Id` crashes a proposal (500)

`llm_traces.trace_id` is the primary key, but the pipeline sets it to the request's trace id, which a
client may supply in `X-Trace-Id` (it is accepted and echoed for correlation). A retry, or a
frontend that keeps one trace id for a session, gets `UniqueViolation: llm_traces_pkey`, which the
caller sees as HTTP 500. Reproduced: two `POST /exceptions/{id}/proposal` with the same `X-Trace-Id`
gave 200 and then 500.

Fix: key `llm_traces` (and `llm_raw_outputs`) by `proposal_id`, and keep `trace_id` as an indexed
non-unique correlation column (migration 0005). Alternatively, store
`f"{trace.trace_id}:{proposal_id}"` as the key.

### A4 (Medium): unsupported fix types block instead of escalating

When the model proposes an action the validator does not support yet (seen live: `add_break` for
MEAL_BREAK_BREACH), every rule returns `violation` with "not supported yet". The case shows as
BLOCKED, which suggests the fix is wrong, when in fact it simply cannot be judged yet. Suggested
outcome: `insufficient_evidence`, so it ESCALATES to the manager, until contract 0.3.0 defines
`add_break`, `void_shift`, `flag_premium` and `acknowledge`. (B3 already makes the message readable.)

### A5 (Medium, confirm intent): early arrivals and late departures are flagged as deviations

The schedule check compares both boundaries with `abs(...)`, so arriving 20 minutes early or leaving
20 minutes late is a SCHEDULE_DEVIATION violation. Policy KA-9/US-6 defines a deviation as a late
arrival or an early departure only. Extra time worked belongs to OVERTIME_RISK. If flagging it is
intended, the policy text should say so; otherwise make the check one-sided, which also reduces
noise in the manager's inbox.

### A6 (Low): `effective_to` boundary differs

The engine treats `effective_to` as inclusive (`work_date > effective_to` means not applicable),
while `PolicyRegistry.resolve` and the pipeline treat it as exclusive (`work_date < effective_to`).
On the boundary date the two disagree. Pick one, exclusive like the registry, and add a test.

### A7 (Low): documentation drift

`RESOLUTION_API.md` still says PostgreSQL is not in Docker or CI (it is, since dcccc0c).
`ATTENDANCE_API.md` still says no mutation endpoints exist and that escalation state is not
persisted (both are now implemented).

### B1 (Medium, fixed): the assistant endpoint was unauthenticated

`POST /assistant/query` accepted anonymous requests and can trigger model calls (cost, denial of
service). It now requires a manager bearer token whenever the attendance store is enabled, the same
rule as the data endpoints. It stays open in the offline demo, where no identity store exists.
Tests: `tests/unit/test_audit_fixes.py`.

### B2 (Low, fixed): new HTTP clients for every proposal

`build_embedder` and `build_provider` created a new HTTP client (connection pool) on every call. The
pipeline calls `build_embedder` per proposal, and Track A's proposal route calls `build_provider` per
request, so every proposal paid a fresh connection to Ollama. HTTP providers and the Ollama embedder
are now shared per configuration (thread-safe). The mock is never shared, because it records calls.
This also fixes Track A's route without changing it.

### B3 (Low, fixed): unreadable blocked reasons

Identical validator reasons are now reported once with the rules they apply to: "MISSING_PUNCH,
OVERLAPPING_SHIFT, …: add_break corrections are not supported yet." Previously the same sentence
repeated six times.
